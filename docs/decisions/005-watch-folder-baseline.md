# החלטה 005 — חיבור לתיקייה קיימת רושם מצב פתיחה

תאריך: 2026-08-17

## הקשר

הסוכן קיבל ב-[004](004-admin-interface-and-agent.md) מקור עבודה שני: תיקייה
מקומית שאליה מגיעים קובצי המצב"ת אוטומטית. הוא סורק אותה כל דקה, מקבץ לפי
קוד רשות, ומעבד כל מועצה שהקבצים שלה השתנו.

התכנון הזה הניח תיקייה שמתחילה ריקה. **התיקייה אצל סבא מתעדכנת כל חודש כבר
שבע שנים** — היא מכילה את כל ההיסטוריה של כל המועצות.

## הבעיה

בסבב הראשון `watch-state.json` ריק, ולכן כל מועצה נראית "השתנתה":

```
state.get(code) == fp   →   None == fp   →   False   →   מעבד
```

כלומר **עצם חיבור התיקייה היה מפעיל טעינה לכל מועצה שיש לה קבצים שם**.
לא "מעלה את כל שבע השנים" — הסוכן בוחר לכל מועצה את הקבצים העדכניים
ביותר — אבל זהו עדכון המוני שאיש לא ביקש, שדורס טבלאות חיות ברגע ההתקנה.

הסיכון האמיתי אינו הנפח אלא **חוסר הכוונה**: ההתקנה אמורה להיות פעולה
בטוחה, לא אירוע טעינה.

## ההחלטה

סבב ראשון מול תיקייה שלא נראתה קודם **רושם את מה שיש בה ויוצא**:

```
09:12:03  INFO   חיבור ראשון לתיקיית המצב"ת: D:\מצבת\נכנס
09:12:03  INFO   נרשם מצב פתיחה - 3 רשויות. הקבצים הקיימים לא יעובדו
09:12:03  INFO   מכאן ואילך יעובד רק מה שיתעדכן בתיקייה
```

`take_baseline()` שומר את טביעת האצבע של כל מועצה שלמה, בלי לעבד דבר.
גם **החלפת תיקייה** נחשבת חיבור חדש — הנתיב נשמר ב-state ומושווה בכל סבב.

### מה כן מעובד אחרי מצב הפתיחה

| מצב | התנהגות |
|-----|---------|
| הגיעו קבצים חדשים למועצה | מעובדים |
| אותם קבצים בדיוק, סבב נוסף | כלום |
| רשות **נוספה למערכת** אחרי הרישום | נטענת בסבב הבא — כך מועצה חדשה נטענת מעצמה |
| הוחלפה התיקייה | מצב פתיחה חדש |

### מוצא חירום

```powershell
venv\Scripts\python.exe worker.py --once --process-existing
```

מתעלם **גם ממצב הפתיחה וגם מהמעקב הפר-מועצתי**. הניסיון הראשון דילג רק על
מצב הפתיחה — ואז המעקב חסם בדיוק את מה שהדגל נועד להריץ, כך שהוא לא עשה
דבר. שני המחסומים חייבים ליפול יחד.

## שינויים נלווים שהבדיקה חשפה

### טביעת האצבע ויתרה על `mtime`

```python
# לפני:  שם : גודל : mtime
# אחרי:  שם : גודל
```

`mtime` משתנה בכל העתקה. כלי שמסנכרן את התיקייה כולה מדי חודש היה נראה
כמו עדכון של **כל** המועצות, וגורר טעינה מחדש של אותם נתונים בדיוק. שם
הקובץ נושא את חותמת משרד החינוך ולכן הוא ייחודי לכל עדכון ממילא.

זו אותה משפחת באגים של [`file_version`](004-admin-interface-and-agent.md):
תאריך הדיסק אינו מאפיין אמין של קובץ מצב"ת. בשתי הפעמים התשובה הייתה
להסתמך על השם.

### `file_version` שובר שוויון בשם

```python
return (1, token, path.name)          # במקום path.stat().st_mtime
```

חוסך קריאת `stat` מכל קובץ בתיקייה של שבע שנים, וגם דטרמיניסטי בין ריצות.
הענף היחיד שעדיין קורא `stat` הוא קובץ בלי חותמת בשם.

### `watch-state.json` בגרסה 2

```json
{
  "version": 2,
  "folder": "D:\\מצבת\\נכנס",
  "baseline_at": "2026-08-17T09:12:03",
  "authorities": { "1400000": "שם:גודל|…" }
}
```

קובץ מגרסה 1 (מילון שטוח) משודרג בלי לאבד את המעקב, אחרת עצם השדרוג היה
מריץ מחדש את כל מה שכבר עלה. הכתיבה אטומית (`tmp.replace`) — הפסקת חשמל
לא משאירה קובץ חצי.

**מחיקת הקובץ שוב אינה מריצה הכול מחדש.** היא מאפסת את המעקב, ולכן הסבב
הבא ירשום מצב פתיחה חדש ולא יעבד כלום. זה היפוך של ההתנהגות הקודמת, והוא
מתועד ב-[agent/README](../../agent/README.md).

### `check_setup.py` מדווח לפני ההתקנה

```
✓ D:\מצבת\נכנס
   174 קובצי CSV בתיקייה כרגע
   בהפעלה הראשונה יירשם מצב פתיחה — הקבצים שכבר בתיקייה לא יעובדו
```

השאלה "מה יקרה ל-174 הקבצים האלה" נענית **לפני** שהסוכן רץ, לא אחרי.

## הבדיקה

תיקייה שמדמה את זו של סבא: 14 עדכונים × 2 מועצות × 6 קבצים = 168 קבצים,
2019→2026, 299MB.

| שלב | תוצאה |
|-----|-------|
| חיבור ראשון | מצב פתיחה, 2 רשויות, **0 עובדו**, 2 שניות |
| סבב חוזר | כלום |
| הגיע עדכון למטה מנשה | ✓ 8,244 — **רק היא** |
| סבב חוזר | כלום |

`students_120` נשארה 4,881 לכל אורך הבדיקה.

[`agent/tests/test_baseline.py`](../../agent/tests/test_baseline.py) מכסה את
ההחלטה עצמה — מה נבחר לעיבוד — כולל שדרוג מגרסה 1, קובץ מצב פגום, וסנכרון
שנגע בתאריכי כל הקבצים.

הבדיקות סינתטיות ואינן נוגעות במסד: הן בונות קובצי CSV מזויפים בתיקייה
זמנית, ולכן רצות על כל מחשב בלי קובצי מצב"ת אמיתיים.

```powershell
venv\Scripts\python.exe tests\run_all.py
```

### מה שהבדיקה שברה

`--process-existing` טען את שתי המועצות, ו-`students_120` קיבלה את התוכן
של מטה מנשה. **הסיבה בפיקסצ'ר**: הוא שכפל את קובצי מטה מנשה תחת קוד
משרד החינוך 5108, כך שהטעינה הייתה נאמנה לקלט גרוע. `check_moe_code`
אינו יכול לתפוס את זה — הוא משווה את הקוד שבשם, והקוד שבשם היה נכון.

הטבלה שוחזרה מהגיבוי שהסוכן לקח רגע קודם: 4,881 שורות, מוסדות משלה,
0 ת"ז משותפות עם 1400000. **זו הפעם הראשונה שמנגנון הגיבוי נדרש בפועל
ועבד.**

## המסקנה

> חיבור מקור נתונים חדש הוא **אירוע קונפיגורציה**, לא אירוע טעינה.

המצב ההתחלתי של מקור חיצוני אינו "שינוי" — הוא נקודת ההתחלה שממנה מודדים
שינויים. סוכן שמתעורר מול עולם מלא צריך קודם לרשום מה הוא רואה.
