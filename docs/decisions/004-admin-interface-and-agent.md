# החלטה 004 — ממשק מנהל, הרשאות מדורגות וסוכן עיבוד

תאריך: 2026-08-13

## הקשר

עד כה המערכת שירתה רשות אחת, וכל פעולת ניהול — יצירת משתמש, הוספת רשות,
טעינת נתונים — דרשה הרצת סקריפט או SQL ידני. הדרישה: **ממשק שסבא יכול
לעבוד איתו לבד**, שמנהל את הלקוחות (מועצות אזוריות), את ההרשאות שלהם,
ואת עדכון הנתונים — בלי מתכנת.

---

## 1. גישה לממשק המנהל — לפי תפקיד, לא לפי סיסמה קסומה

**הבקשה המקורית:** הזנת סיסמה מסוימת במסך הכניסה תעביר למסך המנהל.

**מה שנבנה במקום:** משתמש עם `role = 'super_admin'` מנותב אוטומטית ל-`/admin`.
חוויית המשתמש זהה — סבא מקליד מייל וסיסמה ומגיע לניהול — אבל:

| | סיסמה קסומה | לפי תפקיד |
|---|---|---|
| מי נכנס | לא ידוע | מזוהה בשם |
| דליפה | כל מי שיקבל את הסיסמה | חשבון אחד, ניתן להשהיה |
| אכיפה | בדפדפן בלבד — ניתנת לעקיפה | ב-RLS, בצד השרת |

עם תעודות זהות של אלפי קטינים, בדיקה שרצה בדפדפן אינה הגנה.

---

## 2. הרשאות מדורגות — שלוש רמות היקף

מעבר לשיוך לרשות ("רשות = עולם"), נוספה רמת **היקף בתוך הרשות**:

| רמה | רואה | לפי |
|---|---|---|
| מועצתי | כל תלמידי הרשות | — |
| יישובי | יישובים נבחרים | `SEMEL_YISHUV1` |
| בית-ספרי | מוסדות נבחרים | `SEMEL_MOSAD` |

**ההיקף רק מצמצם, לעולם לא מרחיב.** ה-RLS דורש את שתי הבדיקות:

```sql
using (has_authority('1400000')
       and in_user_scope("SEMEL_YISHUV1", "SEMEL_MOSAD"))
```

נבדק על נתוני אמת: משתמש יישובי קיבל 1,016 תלמידים (פרדס חנה-כרכור),
בית-ספרי 1,282 (מקיף גוונים), מועצתי 8,244 — התאמה מדויקת לספירה במסד.

---

## 3. ניהול משתמשים — Edge Function ולא בדפדפן

יצירת משתמש וקביעת סיסמה דורשות את מפתח ה-`service_role`, שאסור שיגיע
לדפדפן. נבנתה [Edge Function `admin-users`](../../supabase/functions/admin-users/index.ts)
שמחזיקה אותו בצד השרת ומאמתת בעצמה, בכל קריאה, שהקורא הוא מנהל-על —
דרך `service_role` ולא דרך RLS, כדי לא להיות תלויה במדיניות שעלולה להשתנות.

היא גם מאמתת קלט (תפקידים והיקפים מרשימה סגורה, סיסמה ≥ 8), חוסמת
מחיקה והשהיה עצמית, ומתרגמת שגיאות Supabase לעברית.

### שלוש מלכודות בפריסה

1. **`jsr:` אינו נתמך** בסביבת הריצה → `BOOT_ERROR`. יש להשתמש ב-`esm.sh`.
2. **ה-endpoint הישן לא מגדיר `entrypoint_path`** — מחזיר `ACTIVE` והפונקציה
   נופלת. יש להשתמש ב-`/functions/deploy` עם multipart.
3. **ה-CLI של Supabase נכשל ברשת עם סינון תוכן** (`TransportError`).
   הפריסה נעשית מול ה-Management API ב-curl. ראה [server-migration.md](../server-migration.md).

---

## 4. השהיית משתמש — שני רבדים

לחיצה על "השהייה" עושה שני דברים:

1. **ban ב-Supabase Auth** — הכניסה עצמה נכשלת.
2. **`is_suspended` ב-`public.users`** — מנטרל את `has_authority`,
   `in_user_scope` ו-`is_super_admin`.

הרובד השני נדרש כי **טוקן שכבר הונפק נשאר תקף עד שהוא פג** (כשעה).
בלעדיו, מי שהושהה בזמן שהיה מחובר היה ממשיך לראות נתונים.

נבדק: טוקן שנשאר מלפני ההשהיה החזיר 0 תלמידים.

---

## 5. הוספת מועצה מהממשק

הוספת רשות אינה שורה בטבלה — לפי "רשות = עולם" צריך גם טבלת תלמידים
משלה, RLS ואינדקסים. הפונקציה [`create_authority`](../../supabase/migrations/006_create_authority.sql)
עושה הכל בפעולה אחת:

```sql
create table students_{code} (like students_1400000 including all)
```

**קוד הרשות נכנס לתוך שם טבלה**, ולכן מאומת כספרות בלבד — זו ההגנה מפני
SQL injection, לא ניקוי מחרוזות.

---

## 6. מנהל-על רואה את כל הרשויות (מיגרציה 008)

**באג שהתגלה בשימוש:** כרטיסי הלקוח הראו 0 תלמידים לרשויות שלא שויכו
ידנית למנהל, וכניסה לטבלה שלהן החזירה ריק. הסיבה: `has_authority` בדק
רק את `authority_codes`.

התיקון: מנהל-על עובר את הבדיקה לכל רשות — תואם למה שהוא כבר יכול לעשות
(לנהל לקוחות, ליצור רשויות, לשנות הרשאות).

**הבידוד נבדק אחרי השינוי:** משתמש רגיל המשויך ל-1400000 בלבד נחסם
מ-800000 ומ-120. "רשות = עולם" נשמר; רק מנהל-על חוצה.

בנוסף נוסף ניתוב `/students/:code`, כי מסך הטבלה לא קיבל כלל איזו רשות
להציג ותמיד לקח את הראשונה של המשתמש.

## 7. סוכן העיבוד

ה-pipeline הוא pandas — הוא לא יכול לרוץ בדפדפן ולא ב-Netlify. לכן
העלאת קבצים מהאתר שומרת אותם ב-Storage ומסמנת "ממתין", ו**סוכן שרץ על
מחשב נפרד** מבצע את העיבוד.

### תשאול ולא דחיפה

הסוכן שואל כל 5 שניות אם יש עבודה. הוא יושב מאחורי ראוטר ביתי בלי כתובת
קבועה — אף אחד לא יכול לפנות אליו. **אין פורט פתוח ואין שינוי בחומת האש.**

תפיסת העבודה אטומית:

```sql
update moe_uploads set status = 'processing'
 where id = (select id from moe_uploads where status = 'pending'
             order by uploaded_at limit 1 for update skip locked)
```

בלי `skip locked`, שני סוכנים היו יכולים לעבד את אותה העלאה — ומכיוון
שהטעינה עושה `TRUNCATE`, זה היה עלול להשאיר טבלה ריקה.

### חשבון ייעודי ולא `service_role`

התכנון הראשוני נתן לסוכן את המפתח הסודי. **נדחה:** המפתח עוקף כל הגנה,
והוא יושב על מחשב שרץ 24/7 ואינו בשליטה הדוקה. אם ייפרץ — שליטה מלאה
בכל הרשויות, ואין ביטול מהיר.

במקום זאת הסוכן מתחבר כמשתמש רגיל (`agent@matzevet.local`). אם משהו
חשוד — לוחצים "השהייה" באתר והגישה נחסמת מיד.

### גיבוי לפני דריסה

הטעינה עושה `TRUNCATE`. לכן לפני כל עדכון נשמר עותק:

```
agent/backups/students_1400000/students_1400000_2026-08-13_2226.csv.gz
```

CSV דחוס עם כל 165 העמודות, 12 גיבויים אחרונים לכל רשות (~13MB — שנה
של עדכונים חודשיים). טבלה חדשה אינה מגובה.

### הפעלה 24/7

Task Scheduler ולא שירות Windows — מובנה במערכת, בלי כלים חיצוניים.
עולה עם המחשב, רץ תחת `SYSTEM` גם כשאף אחד לא מחובר, מרים את עצמו אם
נפל, ורץ ללא חלון.

## באגים שנתפסו בבדיקות

| באג | תסמין | תיקון |
|---|---|---|
| `COPY` השאיר טרנזקציה פתוחה | הגיבוי עבד, אבל ה-`TRUNCATE` של הטעינה נתקע עד פקיעת זמן | `conn.commit()` ב-`finally` |
| סקריפט האריזה כלל את תיקיית היעד של עצמו | ה-ZIP תפח ל-23GB | חסימת `dist` ו-`backups`, ועצירה מעל 50MB |
| `.gz` לא נחסם באריזה | גיבויים עם ת"ז כמעט נכנסו לחבילה | הוספת `.gz` ו-`.zip` לרשימה |
| `supabase-js` מסתיר את גוף השגיאה | "Edge Function returned a non-2xx status code" בלי פירוט | קריאה מ-`error.context` |
| `placeholder="••••••••"` | נראה כמו שדה מלא — לא היה ברור אם הוקלד משהו | placeholder טקסטואלי + משוב חי |
