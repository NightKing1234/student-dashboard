# נתונים תוספתיים — אפיון תשתית

מסמך אפיון. **טרם מומש, וה-SQL כאן אינו בתיקיית המיגרציות בכוונה** —
כדי שהרצה של `run_migrations.py` לא תיצור את הטבלאות לפני שסבא אישר
את רשימת השדות.

## הצורך

היום המערכת פסיבית: נתוני משרד החינוך נדרסים כל חודש, ואין לאף אחד דרך
להוסיף מידע משלו. סבא (הערה 17 + התמלול):

> *"אני רוצה שהמפעילים, הלקוחות, יוכלו למלא תוכן... אני קורא לזה נתונים
> תוספתיים. את זה אני עושה בטבלאות נפרדות, שהן מקושרות באינדקס של מספר
> תעודת זהות... אותה תעודת זהות תמצא בטבלת התוספתיים את אותם נתונים
> שנשמרו לי מהמילוי."*

דוגמאות לשימוש שנתן: גביית אגרות חוץ, חיבור לנתוני הסעות, כוח אדם.

**התזמון שהוא קבע בעצמו:** *"שלב ב' — אנחנו רוצים קודם לצאת לשיווק עם
הנתונים הפסיביים, אבל במקביל או בהמשך להגיע גם ליכולת לתת לאנשים מסכי
עבודה אקטיביים."*

## העיקרון: דלתא, לא דריסה

זה ההבדל המהותי מהטבלה הראשית:

```
עדכון חודשי:
  students_{code}        →  TRUNCATE + טעינה מחדש     (נדרס)
  students_{code}_extra  →  מוחקים את מי שנגרע,
                            מוסיפים ת"ז של מי שנוסף    (נשמר)
```

תלמיד שנגרע — הנתונים התוספתיים שלו נמחקים ממילא. תלמיד חדש — נוצרת לו
שורה עם ת"ז בלבד, בלי תוכן. תלמיד שנשאר — **התוכן שהוזן עליו שורד**.

## מקור רשימת השדות

`Itay_Modules/tables/Additional_fields_11.xlsx` כבר מגדיר 42 עמודות
שסבא מתחזק באקסס. מתוכן, אלה שנראות רלוונטיות לעריכה ידנית באתר:

| קבוצה | שדות |
|--------|------|
| חינוך מיוחד | חינוך מיוחד תלמיד · אפיון וזכאות · משבצת · סלים אישיים · סל זכאות בכיתה רגילה · זכאי שעות סייעת · מספר שעות זכאות סייעת |
| הסעות | זכאי הסעה ח"מ · זכאי ליווי בהסעה · זכאי הסעה קפיטה (ברשות / מיפוי) |
| כספים | אגרת חוץ |
| רפואי | מגבלה רפואית · קופת חולים תלמיד |
| שיוך | תלמיד חוץ · תלמיד תושב · תלמיד תושב לומד בחוץ · תלמיד במוסד ברשות |
| מסגרות | לידה עד 3 · גן חובה 4-6 · קידום נוער · חינוך ביתי · מטופלי קב"ס · כיתת חרוב · סטטוס היל"ה |
| חירום | מפונים לבירור · מפונים מאושרים |
| חופשי | הערות · הערה · שכבה וכיתה בפועל · קבצים מצורפים |

**שאלה לסבא:** אילו מהן באמת נערכות ידנית, ואילו מחושבות? חלקן (תלמיד
חוץ, לידה עד 3) ייגזרו ממילא מהנתונים או מקליטת דרג ב', ואין טעם לפתוח
אותן לעריכה.

## הצעת סכימה

```sql
-- טבלה תוספתית אחת לכל רשות, מקושרת בתעודת זהות.
create table public.students_{code}_extra (
  "MISPAR_ZEHUT"   text primary key,
  -- שדות לדוגמה; הרשימה הסופית לפי אישור סבא
  agrat_chutz      boolean,
  saya_hours       numeric,
  medical_note     text,
  kupat_cholim     text,
  notes            text,
  updated_at       timestamptz not null default now(),
  updated_by       uuid references public.users(id)
);

alter table public.students_{code}_extra enable row level security;

-- קריאה: כמו הטבלה הראשית — שיוך לרשות וגם היקף בתוכה
create policy students_{code}_extra_read on public.students_{code}_extra
  for select to authenticated
  using (public.has_authority('{code}'));

-- כתיבה: רק למי שיש לו הרשאת עריכה מפורשת
create policy students_{code}_extra_write on public.students_{code}_extra
  for all to authenticated
  using (public.has_authority('{code}') and public.may_edit_extra())
  with check (public.has_authority('{code}') and public.may_edit_extra());
```

### הרשאת עריכה נפרדת

סבא: *"אולי לייצר איזושהי הרשאת עריכה, שיש כאלה שאפשר להגדיר להם אותם
רק לצפייה."*

מוצע דגל `can_edit_extra boolean` ב-`users`, ופונקציה `may_edit_extra()`
במקביל ל-`has_authority`. **הרשאת צפייה אינה מקנה הרשאת עריכה** — זו
הסיבה לשתי מדיניות נפרדות ולא לאחת.

### עדכון הדלתא

מתבצע בסוכן, מיד אחרי טעינת הטבלה הראשית ובאותה טרנזקציה:

```sql
delete from students_{code}_extra e
 where not exists (select 1 from students_{code} s
                    where s."MISPAR_ZEHUT" = e."MISPAR_ZEHUT");

insert into students_{code}_extra ("MISPAR_ZEHUT")
select s."MISPAR_ZEHUT" from students_{code} s
on conflict do nothing;
```

## מה נדרש כדי להתחיל

1. **אישור סבא על רשימת השדות** ועל אילו מהן ניתנות לעריכה.
2. החלטה אם ההרשאה היא ברמת משתמש (דגל אחד) או ברמת שדה.
3. מיגרציה + הרחבת `create_authority` כך שרשות חדשה תקבל גם טבלה תוספתית.
4. שינוי בסוכן לעדכון הדלתא — **שינוי בשרת של סבא**.
